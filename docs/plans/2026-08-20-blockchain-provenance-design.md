# 区块链存证与计算溯源设计

## 目标

在不阻断现有策略和查询业务的前提下，为普通策略、联邦策略、计算过程和异常事件增加可验证的区块链存证，并由唯一超级管理员查看、校验和重试。

## 架构

MySQL `attempt` 是业务事实来源。策略写入后由数据库触发器可靠创建存证任务，后台执行器通过条件更新抢占任务。任务从业务表读取数据，生成字段顺序固定的规范化 JSON，并计算 SHA-256。配置了区块链后，执行器发送一笔零金额以太坊交易到签名账户自身，把 `0x` 加摘要作为交易 input；取得成功回执和区块高度后才标记 `CONFIRMED`。未配置或网络失败不影响业务数据。

现有 `DataStorage` 合约只支持固定普通策略字段，无法覆盖 SHA-256、联邦策略和异常记录，因此本阶段不假装复用该合约完成通用存证。后续可部署专用 Anchor 合约，再在不改变数据库模型的情况下替换交易提交器。

## 数据模型

- `blockchain_anchor`：业务类型与 ID、trace ID、规范化载荷、SHA-256、状态、重试信息、链 ID、发送地址、交易哈希、区块高度和确认时间。
- `computation_trace`：数据流、阶段、时间范围、输入/输出摘要、算法、异常标记和可公开元数据。
- `policy` 与 `policy_mpc` 的插入触发器负责创建 `PENDING` 任务，避免应用进程崩溃造成任务丢失。

## 安全边界

链上仅保存摘要，不保存原始交通数据、完整密文、AES 密钥、MAC 密钥、数据库密码或私钥。私钥只允许由 `BLOCKCHAIN_PRIVATE_KEY` 环境变量注入。源码中旧私钥删除并视为失效。管理员 API 只返回交易和验证信息，不返回秘密配置。

## 管理员体验

管理员页面新增“区块链存证”页签，显示待处理、处理中、已确认、失败和待配置状态；支持查看规范化载荷、重新计算摘要、打开区块浏览器以及安全地手动重试。策略详情和异常回溯展示其关联存证。

## 失败与并发

执行器使用唯一业务键和 `UPDATE ... WHERE status IN (...)` 抢占，保证同一时刻只有一个执行者。超时的 `PROCESSING` 会恢复；网络失败使用有限指数退避；只有交易回执状态成功才确认。数据库成功、链上尚未确认属于明确展示的最终一致性状态。
